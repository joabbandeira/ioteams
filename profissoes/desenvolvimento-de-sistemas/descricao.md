# Desenvolvimento de Sistemas

Este campo reúne competências para transformar necessidades em sistemas utilizáveis e mantê-los adequados ao longo do tempo. Inclui requisitos, experiência e acessibilidade, interfaces, serviços e integração, dados e validação. O resultado é o comportamento integrado observado por quem usa o produto; uma tela isolada ou uma API que compila não basta para demonstrá-lo.

## Propósito e recorte

O desenvolvimento relaciona o problema a escolhas concretas: quais informações apresentar, como uma operação falha, onde os dados vivem e como verificar a entrega. As disciplinas colaboram continuamente. Uma decisão de interface pode revelar uma regra de negócio ausente; um teste pode mostrar que o contrato de um serviço é ambíguo; uma restrição de dados pode exigir esclarecer o requisito.

Este acervo usa exemplos de catálogo e busca para conectar essas decisões. As fontes técnicas primárias incluem [WCAG 2.2](https://www.w3.org/TR/WCAG22/), [OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html) e a documentação de [integridade referencial no SQLite](https://www.sqlite.org/foreignkeys.html). Elas sustentam partes do trabalho, sem impor uma stack universal.

## Relações no catálogo

Conhecer esta profissão não define sozinho uma função na equipe. Um profissional pode contribuir com mais de uma disciplina e relacionar suas stacks no perfil. Em uma equipe Scrum, especialistas de interface, dados ou qualidade podem atuar como Developers. A responsabilidade de valor do PO e a facilitação do SM permanecem distintas, conforme a profissão de [Scrum](../metodologia-agil-scrum/descricao.md).

Este recorte enfatiza construir e evoluir o comportamento do sistema. Decisões arquiteturais e operação se relacionam a outros campos do catálogo conforme a demanda, sem exigir que toda profissão participe de toda entrega. Os [conceitos de profissões](../../docs/conceitos/02-profissoes.md) e sua [organização](../../docs/conceitos/03-organizacao-das-profissoes.md) explicam essa composição.

## Aplicação e limites

Para uma busca de competências, a equipe precisa entender os termos usados, oferecer interação acessível, definir a consulta, tratar estados vazios e verificar o resultado. Um protótipo pode responder dúvidas de linguagem antes de existir uma persistência definitiva. A profundidade de cada atividade depende dos riscos e do objetivo; o ciclo não exige uma sequência rígida de departamentos ou documentos extensos.
