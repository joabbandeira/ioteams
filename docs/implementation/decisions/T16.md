# T16 — Painel operacional e composição segura

## Decisões de implementação

- Mantida a identidade existente LISA: React/Tailwind/Radix, paleta, fontes locais, temas e demo. `app.tsx` agora é somente o entry point; demo, shell operacional, cliente, primitives e vistas têm owners separados.
- Build padrão operacional permanece em `painel/dist`, ignorado. `build:demo` define o modo fictício em compilação e publica somente quando explicitamente chamado. `/demo` no servidor local monta a simulação sem cliente operacional. O HTML publicado na árvore não foi alterado nesta tarefa.
- O servidor recebe o HTML compilado por composição confiável; serve somente rotas exatas em loopback, com Host/Origin existentes e CSP de script por hash. Não há endpoint de arquivos arbitrários ou CORS.
- CLI e navegador têm sessões independentes. O launcher consome o bootstrap da CLI como antes e publica `browser-access.html` privado/0600 com uma segunda capacidade, de uso único e validade de até dois minutos. O operador copia o código para um formulário na mesma origem; não há segredo em URL, stdout, log ou armazenamento persistente do browser. A liberação confere identidade do arquivo antes de removê-lo.
- `/api/v1/bindings` é autenticado e usa callback puro separado de `planningPolicy`. A projeção contém somente demanda, repositório e plano confiável inicial. Nunca chama o callback que cria workspace em GET e não expõe arquivo de política, runtime home, corpus roots ou instruções confiáveis.
- Contratos browser usam subpaths puros de storage/entities, runtime/planning-contracts e knowledge/contracts. O schema de busca foi movido sem alteração e reexportado no caminho anterior. `@ioteams/server/contracts` é o ponto compartilhado; nenhuma regra de RAG, persistência ou domínio foi duplicada na UI.
- Limites de projeto, equipe, slots, branch, remote, checks e escopo são somente leitura. Objetivo/requisitos são configuráveis dentro do binding; critérios de competência continuam no serviço. Demanda após tentativa permanece imutável, inclusive com lacunas. Não há catálogo CRUD autônomo ou replanejamento do mesmo ID.
- A revisão separa Product Goal/Backlog, Sprint Goal/Backlog, DoD, tarefas, checks, responsabilidades e citações. Aprovar envia o hash exato; iniciar run é outra confirmação. Progressão manual de tarefa operacional não é oferecida. Controles de run e aprovações concretas delegam à API versionada.
- Os registros completos de eventos Scrum não estão disponíveis no contrato atual; a cadência informa essa limitação. Metadata SSE só provoca releitura dos registros. A exposição de eventos e a prova de recuperação/encerramento de host permanecem na etapa de integração correspondente.

## Resiliência e revisão

Leituras são canceláveis; snapshots antigos não substituem os novos. Busca tem debounce/IME/clear e proteção contra respostas fora de ordem. Mutações são pessimistas, sem retry automático, com chave idempotente e bloqueio síncrono. Resultado incerto bloqueia reenvio e pede reconciliação. Sessão expirada preserva o draft não sensível em memória e fecha controles. Formulários usam schemas compartilhados, noValidate, erro associado e foco.

O achado T16-R1 foi reproduzido: após escolher um subset válido e planejar, o reload reconstruía checkboxes do repertório profissional. Estados proposed/approved agora exibem exclusivamente `proposal.requirements`; tentativas sem snapshot completo mostram indisponibilidade e lacunas, sem defaults congelados. A regressão cobre subset sem Git → proposta/aprovação → reload e ausência de checkboxes reconstruídos em needs_competency.

A navegação usa foco no commit visual, sem requestAnimationFrame tardio que possa roubar a primeira edição. Confirmações Radix restauram foco ao disparador, com Cancelar inicial. A regressão também cobre Escape/restauração, tema, popup e viewport de 390px. O overflow identificado vinha do botão de tema herdando largura de 30px do demo; a regra operacional foi delimitada, preservando a variante fictícia.

## Dependências e evidências

Foram declaradas dependências já instaladas de workspace/core/server e Zod no painel. `npm install --package-lock-only --ignore-scripts --offline` removeu registros opcionais de Lightning CSS que já existiam no lock. Esses registros foram preservados integralmente a partir da âncora; o diff final do lock contém somente as três dependências do painel. Não houve instalação global ou alteração de versão/binding nativo.

Auditoria premium strict e auditoria Markdown são locais, com relatórios fora do Git no diretório de continuidade. O linter oficial DESIGN.md retornou zero erros; avisos de tokens órfãos refletem o modelo B, em que CSS é canônico e os componentes consomem variáveis em runtime. Tests E2E usam SQLite/índice/serviços reais e hosts simulados; não fazem login ou inferência nativa. Traces do browser ficam desligados para não arquivar credenciais de sessão da fixture; screenshots de estados sem credenciais podem ser usados na inspeção visual.

O teste legado de tooling exigia igualdade de bytes entre demo e operacional e título LISA no build padrão. Isso é incompatível com a separação aprovada; o coordenador reconciliou somente esse path em r5. O teste agora exige títulos próprios, bundles distintos, demo sem API/cliente operacional e preservação do HTML publicado no build padrão. O título do demo foi identificado explicitamente como fictício. Nenhum teste fora do escopo inicial foi alterado antes dessa reconciliação.

A validação final, o SHA local e a pendência de push são reportados no recibo. Não há push, tag, alteração de relay, acesso a runtime pessoal ou acesso ao runtime autenticado do produto por este worker.

A primeira execução de runtime-execution terminou43/44, com timeout10s no caso de aprovação RPC incerta, durante sobreposição com runtime-policy. Essa observação permanece preservada no recibo r4; contenção é uma hipótese, não causa provada. A comparação isolada e os seis grupos sequenciais são condições da validação r5, sem alteração de timeout, asserções ou runtime.

A validação de requisitos vazios é associada ao grupo de competências, preservando o objetivo válido. A regressão verifica foco, aria-invalid/describedby e ausência de POST de planejamento inválido.
